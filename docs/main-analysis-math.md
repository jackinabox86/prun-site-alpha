# The Math Behind the Per-Ticker Analysis

This document explains, formula by formula, what happens when you request the analysis/report
for a single ticker (e.g. `GET /api/report?ticker=CBS&exchange=ANT&priceType=bid`). Every
statement is grounded in the code; each section cites the source file and line numbers of the
formulas it describes.

Source map:

| Concern | File |
|---|---|
| HTTP entry point | `app/api/report/route.ts` |
| Report assembly, ranking, top-20 | `src/server/report.ts` (`buildReport`) |
| Scenario exploration + pruning | `src/core/engine.ts` (`findAllMakeOptions`, `bestOptionForTicker`, `pruneForDiversity`, `pruneByInputCostShare`) |
| Tree aggregation (area, capex, buffer) | `src/core/engine.ts` (`buildScenarioRows`) |
| ROI metrics | `src/core/roi.ts` |
| Input payback | `src/core/inputPayback.ts` |
| Price lookup | `src/core/price.ts`, `src/core/maps.ts` |
| Scenario naming | `src/core/scenario.ts` |
| Input data / precomputed costs | `src/lib/loadFromCsv.ts`, `public/data/recipes-dynamic.csv`, `scripts/calculate-dynamic-costs.ts` |
| Precomputed "best recipe" guidance | `src/server/bestRecipes.ts`, `src/server/cachedBestRecipes.ts` |

## 1. Pipeline overview

```
ticker ──► recipes for ticker (RecipeMap, one row per recipe variant)
              │  for each recipe: enumerate BUY vs MAKE for every input
              ▼
        scenario tree (each leaf-to-root assignment = one MakeOption)
              │  recursion to depth 3, with pruning at each level
              ▼
        flat list of MakeOptions for the root ticker
              │  buildScenarioRows(): normalize area/capex over the subtree
              ▼
        rank by Profit/Area at full capacity ──► best, top20, topDisplayScenarios
```

Steps, as executed by `buildReport()` (`src/server/report.ts:24–523`):

1. **Load data.** Recipes and prices come from CSVs (`src/lib/loadFromCsv.ts`). Each recipe row
   carries the recipe's outputs/inputs and *precomputed, exchange-specific* cost columns
   (`WfCst-<EX>`, `Deprec-<EX>`, `AllBuildCst-<EX>`; see §2 and §7).
2. **Load the precomputed BestMap** for the selected exchange
   (`report.ts:90–92`) — a per-ticker "best known scenario" table generated offline by
   `src/server/bestRecipes.ts`. It is *always* the `bid`-priced table, regardless of the
   pricing mode you selected for the report (`report.ts:88–92`). It guides deep levels of the
   recursion (§3, §4).
3. **Explore scenarios.** `findAllMakeOptions(ticker, …, depth = 0, exploreAllChildScenarios = true)`
   (`report.ts:393`) enumerates, for the root ticker, every recipe variant × every BUY/MAKE
   assignment of its inputs, recursively, with pruning (§3–§4). Each result is a `MakeOption`
   (`src/types.ts:62–98`): a fully-specified production plan plus its per-batch economics.
4. **Aggregate each plan's tree.** For every option, `buildScenarioRows(option, 0, capacity, false)`
   computes subtree area, build cost, and input buffer, normalized to the root building running
   at full capacity (§5).
5. **Rank and report.** Options are sorted by `subtreeProfitPerArea` descending
   (`report.ts:410–416`); the report returns the best option, the top 20 raw options, and the
   top 20 *display scenarios* (one representative per structurally distinct plan), each
   decorated with ROI and payback metrics (§6).

## 2. Per-recipe unit economics

All quantities below are **per batch** (one run of the recipe) unless noted. The same block of
arithmetic appears in all three option builders in `src/core/engine.ts`
(root exploration: lines 1234–1290; single-best child: 815–885; all-options helper: 474–536).

### 2.1 Inputs from the recipe CSV

Each recipe row (see `public/data/recipes-dynamic.csv`, generated by
`scripts/calculate-dynamic-costs.ts`) provides:

| Column | Meaning |
|---|---|
| `Output1CNT/MAT` … | outputs per batch; output 1 is "the" ticker, outputs 2+ are byproducts |
| `Input1CNT/MAT` … `Input10…` | inputs per batch |
| `Runs P/D` | `runsPerDay` = batches/day = 1 / (recipe duration in days) — this is the per-day normalization |
| `Area` | area (m²) of the producing building |
| `AreaPerOutput` | `Area / (runsPerDay × Output1CNT)` = m² of building per unit of daily output |
| `WfCst-<EX>` | workforce cost per batch = (daily workforce consumable cost at exchange EX ask prices) / `runsPerDay` (`calculate-dynamic-costs.ts:528–552, 619–620`) |
| `Deprec-<EX>` | depreciation per batch = (production building cost / 180 days) / `runsPerDay` (`calculate-dynamic-costs.ts:596–598, 622–623`) |
| `AllBuildCst-<EX>` | one-time capex: production building + prorated habitation buildings, at exchange EX prices (`calculate-dynamic-costs.ts:555–594, 625–626`) |

So workforce and depreciation are already normalized per day upstream and converted to
per-batch by dividing by `runsPerDay`; the engine works per batch and multiplies by
`runsPerDay` when it needs per-day numbers.

### 2.2 Revenue

With `P_sell(t)` = the price of ticker `t` at the selected exchange and price type
(`findPrice`, `src/core/price.ts:4–17`; missing/zero prices are `null`, `src/core/maps.ts:35–37`):

```
totalOutputValue = Output1CNT · P_sell(output1)          (only if a price exists)
                 + Σ_{j≥2} OutputjCNT · P_sell(outputj)  (byproducts, only priced ones)

byproductValue   = the Σ_{j≥2} part alone
```

(`engine.ts:1113–1138`.) A recipe whose main output has no market price is still explored — its
COGM is still meaningful for cost chains — but its profit terms are treated as 0 (see below).

### 2.3 Input cost — the BUY/MAKE dichotomy

For each input `i` with per-batch amount `n_i`, a scenario chooses either:

* **BUY**: `inputCost_i = n_i · P_buy(i)`, where `P_buy` is the **ask** price on regular
  exchanges, or the selected pp7/pp30 price on UNV (`getInputPriceType`, `engine.ts:19–21`).
  The BUY branch only exists if the input has a market price (`engine.ts:1167`).
* **MAKE(c)**: `inputCost_i = n_i · COGM_c`, where `c` is a child MakeOption for that input
  ticker and `COGM_c` is its cost of goods manufactured per unit (§2.5). The MAKE branch
  additionally accrues an **opportunity cost** `n_i · baseProfitPerOutput_c` — the profit the
  child stage forgoes by feeding its output to the parent instead of selling it
  (`engine.ts:1208–1210`).

Summing over inputs:

```
totalInputCost       = Σ_i inputCost_i
totalOpportunityCost = Σ_{i ∈ MAKE} n_i · baseProfitPerOutput_(child_i)
```

Note: if an input has *neither* a buy price *nor* any child MAKE option, the branch list for
that input is empty and the whole recipe yields **zero** scenarios (`scenarios = branched` with
`branched = []`, `engine.ts:1230`).

### 2.4 Profit per batch and per day

(`engine.ts:1234–1238, 1275–1276`)

```
totalProductionCost = totalInputCost + WfCst + Deprec
baseProfit          = totalOutputValue − totalProductionCost        (per batch)
finalProfit         = baseProfit − totalOpportunityCost             (per batch, "adjusted")

baseProfitPerDay    = baseProfit  · runsPerDay
profitPerDay        = finalProfit · runsPerDay
```

`baseProfit` is the headline margin: because MAKE inputs are costed at the child's COGM, a
parent's `baseProfit` captures the margin of the *entire* chain below it. `finalProfit` answers
a different question — "how much better is this than just selling the intermediates?" — by
subtracting what the child stages could have earned on the open market.

### 2.5 Per-unit figures and COGM

(`engine.ts:1240–1250`)

```
cogmPerOutput       = (totalProductionCost − byproductValue) / Output1CNT
baseProfitPerOutput = baseProfit  / Output1CNT     (forced to 0 if output1 has no price)
adjProfitPerOutput  = finalProfit / Output1CNT
valuePerOutput      = totalOutputValue / Output1CNT
```

COGM credits byproduct revenue against cost, so it is the net cost of one unit of the main
output. This is the number that flows *upward*: when a parent MAKEs this ticker, it pays
`cogmPerOutput` per unit — which recursively includes workforce, depreciation, and the COGM of
everything below.

### 2.6 Area and buffer primitives

(`engine.ts:1252–1260`)

```
selfAreaPerDay = AreaPerOutput                          (m² per unit of daily output)
               = Area / (runsPerDay · Output1CNT)       (fallback if column missing)

inputBuffer7   = 7 · (totalInputCost + WfCst) · runsPerDay
```

`inputBuffer7` is the working capital needed to hold 7 days of inputs + workforce consumables
for this stage at full utilization (depreciation deliberately excluded — it is not a cash
outlay you stockpile).

## 3. The recursive BUY/MAKE exploration

`findAllMakeOptions` (`engine.ts:902–1300`) is called by the report with `depth = 0` and
`exploreAllChildScenarios = true` (`report.ts:393`).

### 3.1 Branch product per recipe

For one recipe with inputs `1..k`, the scenario list is built by a running Cartesian product
(`engine.ts:1150–1231`): starting from one empty scenario, each input multiplies the list by
its branch count

```
b_i = [1 if input i is buyable] + (number of surviving child MAKE options for input i)

options per recipe = Π_{i=1..k} b_i
```

and the ticker's option count is the sum over its recipe variants. Without pruning this is
exponential in chain depth: each child option count is itself such a product.

### 3.2 Recursion depth

For each input, children are fetched with

```ts
findAllMakeOptions(inputTicker, …, depth + 1, depth <= 2 && exploreAllChildScenarios, …)
```

(`engine.ts:1075–1089`). Because the flag is computed at the *parent's* depth, full
combinatorial exploration runs at **depths 0, 1, 2, and 3**. At depth 4 the flag is false and
the call short-circuits (`engine.ts:918–963`):

* If the BestMap entry for the ticker carries `top3DisplayScenarios`, it returns up to **3**
  options matching those precomputed scenario shapes (`topDisplayScenarioOptionsForTicker`,
  `engine.ts:182–220`).
* Otherwise it returns **one** option: `bestOptionForTicker` (`engine.ts:552–894`), which
  builds this ticker's recipes with each input resolved to BUY or its single recursive best
  child, then picks the option whose scenario string exactly matches the BestMap scenario, or,
  failing that, the option with the highest Profit/Area (`engine.ts:872–888`). This
  single-best chain recurses to unbounded depth but explores no alternatives; cycles are
  guarded by a `seen` set (`engine.ts:570–572`) and results are memoized (`BEST_MEMO`).

**Practical note:** in the live report path the BestMap is produced by `convertToBestMap`
(`src/server/cachedBestRecipes.ts:86,106`), which *drops* `top3DisplayScenarios`. So at
depth ≥ 4 the report effectively always uses the single-best chain. The 3-way variant only
operates during offline best-recipes generation, which uses the enhanced map
(`src/server/bestRecipes.ts:298–371`).

Memoization: full exploration results per (exchange, priceType, ticker, constraints) are
cached in `ALL_SCENARIOS_MEMO` (`engine.ts:1294–1297`); both caches are cleared at the start of
every report request (`report.ts:41`, needed because extraction mode is not part of the key).

## 4. Pruning: what is cut, where, and why

Three mechanisms keep the product `Π b_i` under control.

### 4.1 Top-N + diversity pruning (`pruneForDiversity`, `engine.ts:97–127`)

Applied to each input's child option list *after* the recursive call:

* **depth 0** (root's direct inputs): keep top **7** (`engine.ts:1092–1094`)
* **depth 1** (grandchild options): keep top **3** (`engine.ts:1095–1098`)
* depths 2–3: no diversity pruning at this step (only 4.2 below)

Mechanics: every child option is scored by its own standalone Profit/Area at full capacity
(`buildScenarioRows(opt, 0, capacity)`), the top N are kept, **plus** the best-scoring
representative of every *display scenario* — the scenario string with all nested `[…]` detail
stripped (`scenarioDisplayName`, `src/core/scenario.ts:39–52`). So
`"Make C_5 [Make HCP_2 [...]] | Buy H"` and `"Make C_5 [Buy HCP] | Buy H"` are the same display
scenario, but `"Buy C | Buy H"` is a different one and is guaranteed to survive with its best
variant. The kept set can therefore exceed N. Rationale: N keeps the likely winners; the
one-per-shape rule keeps the UI's scenario browser complete (every structurally distinct plan
appears at least once).

### 4.2 Cost-share adaptive pruning (`pruneByInputCostShare`, `engine.ts:133–176`)

Applied once per recipe, before branching, at every exploring depth (`engine.ts:1105`). Each
input's cost contribution is estimated as its buy cost (ask), or, if unpriced, the COGM of its
first child option × amount. With `share_i = cost_i / Σ cost`:

| Cost share | Child options kept |
|---|---|
| `< 5%` | 1 (first = best P/A) |
| `5% – 15%` | `pruneForDiversity(…, 2)` |
| `15% – 30%` | `pruneForDiversity(…, depth == 0 ? 5 : 3)` |
| `> 30%` | untouched |

Rationale: whether you buy or make a component that is 3% of your cost basis barely moves the
parent's P/A, so exploring 7 ways to make it is wasted work; the big-ticket inputs keep their
full option sets.

### 4.3 BestMap collapse at depth ≥ 4 (§3.2)

Beyond three levels of explored alternatives, every deeper ticker resolves to its precomputed
best chain (or top-3 shapes, when available). The BestMap itself was generated bottom-up in
dependency order with `exploreAllChildScenarios = false` (`bestRecipes.ts:302–318`), i.e. each
ticker's best was chosen assuming its children take *their* best — a greedy dynamic program.

### 4.4 What optimality can be lost

* **Greedy child scoring.** Children are ranked by their *standalone* P/A, but what the parent
  actually consumes is the child's `cogmPerOutput` (and its area footprint). A child option
  with mediocre standalone P/A but lower COGM could produce a better *parent* P/A; if it falls
  outside the top-N and isn't the best of its display shape, it is lost.
* **Diversity keeps the wrong representative.** The per-shape representative is the best by
  the child's own P/A, which is not necessarily the variant that best serves the parent.
* **Cost-share estimates are estimates.** Shares are computed from ask prices / first-option
  COGM before exploring, so an input just under a threshold gets clipped even if a cheaper MAKE
  chain would have raised its true relevance.
* **Stale/mismatched deep guidance.** Depth ≥ 4 chains and the BestMap scenario matching are
  driven by a table computed with `bid` sell pricing (`report.ts:88–92`) on a schedule, so with
  `ask`/`pp7`/`pp30` pricing or fast-moving prices, deep subtrees may follow a plan that is no
  longer the true optimum. Also, `bestOptionForTicker` *prefers* the BestMap scenario string
  over the recomputed best-P/A option (`engine.ts:888`).
* Within one recipe, per-input pruning is otherwise safe to combine independently: scenario
  cost is additive across inputs, so the parent optimum over the *surviving* child sets is
  found exactly by the Cartesian product.

The tradeoff is deliberate: exact search over a 4-level chain with, say, 4 inputs × 6 recipes
per level is astronomically large; with the caps, each recipe's product is bounded by roughly
`Π (1 + 7 + #shapes)` at the root and shrinks quickly below, keeping reports interactive while
preserving (a) the near-optimal head of the distribution and (b) at least one representative of
every plan shape.

## 5. Aggregation over the tree: `buildScenarioRows`

(`engine.ts:1302–1412`.) Given an option and a demand `amountNeeded` (units/day of its output),
this walks the MAKE subtree and answers: *how much area, capex, and buffer does the whole chain
need, normalized to the root building running flat out?*

### 5.1 Run-rate matching

```
demandUnitsPerDay      = amountNeeded            (root: Output1CNT · runsPerDay = full capacity)
runsPerDayRequiredHere = demandUnitsPerDay / Output1CNT
childDemand_i          = n_i · runsPerDayRequiredHere        (units/day of input i)
```

(`engine.ts:1308–1314, 1344`.) Each MAKE child is recursed with its own demand, so a child
that is only 20%-utilized contributes only 20% of a building.

### 5.2 Area

(`engine.ts:1330–1334, 1352, 1362–1368`)

```
scaledSelfAreaNeeded    = selfAreaPerDay · demandUnitsPerDay      (fractional building allowed)
childrenAreaNeededSum   = Σ_children subtreeAreaNeededPerDay(child at childDemand)

childrenAreaAtCapacity  = (childrenAreaNeededSum / runsPerDayRequiredHere) · runsPerDay
subtreeAreaPerDay       = Area_full_self + childrenAreaAtCapacity      ("own denominator")
subtreeAreaNeededPerDay = scaledSelfAreaNeeded + childrenAreaNeededSum ("for parent")
```

Two parallel figures: the *needed* figure is demand-prorated and flows upward to the parent;
the *own-denominator* figure re-scales the children from "what this stage currently demands" to
"what this stage would demand at full capacity" and adds one full copy of the stage's own
building. At the root (demand = capacity) the two coincide. Area is treated as continuous —
capacity matching assumes you can build fractional buildings (or, equivalently, amortize shared
buildings across lines).

### 5.3 Profit per area — the primary metric

(`engine.ts:1316–1321, 1394–1397`)

```
subtreeProfitPerArea = baseProfitPerDay / subtreeAreaPerDay
```

Numerator: the **base** (not opportunity-adjusted) profit per day of *this stage only*. That is
correct for the chain because MAKE inputs are priced at child COGM, so all downstream margin
already lands in the parent's `baseProfit`; adding child profits would double-count.
Denominator: the full-capacity area of the entire chain. Result: currency per m² per day for
the vertically-integrated line. (An adjusted-profit variant is computed at
`engine.ts:1323–1328` but is not used for ranking.)

### 5.4 Build cost and input buffer

Both follow the same two-track scaling as area (`engine.ts:1371–1392`), with the stage's own
contribution prorated by utilization:

```
scaledSelfBuildCostNeeded  = AllBuildCst · (runsPerDayRequiredHere / runsPerDay)
subtreeBuildCost           = AllBuildCst + (Σ child buildCostNeeded / runsRequired) · runsPerDay

scaledSelfInputBuffer7Needed = inputBuffer7 · (runsPerDayRequiredHere / runsPerDay)
subtreeInputBuffer7          = inputBuffer7 + (Σ child bufferNeeded / runsRequired) · runsPerDay
```

Note a subtlety: `inputBuffer7` of a parent already contains the *cost* of MAKE inputs (at
COGM) in `totalInputCost`, and the subtree figure then also adds the children's own buffers
(their raw inputs + workforce), so the broad buffer counts working capital at every stage of
the pipeline — intentional if each stage actually holds 7 days of its own inputs.

## 6. Ranking and report metrics

`buildReport` ranks all root options by `subtreeProfitPerArea` evaluated at root full capacity
(`report.ts:410–416`) and emits:

* **`best`** — the top option, decorated with metrics (`report.ts:419–444`);
* **`top20`** — the 20 best raw options (`report.ts:448–471`);
* **`topDisplayScenarios`** — options grouped by display scenario, best representative each,
  re-sorted, capped at 20 (`report.ts:474–509`).

Per-option metrics (`b = baseProfitPerDay`):

```
Profit/Area (primary)     PA        = subtreeProfitPerArea              §5.3

ROI narrow (days)         ROI_n     = AllBuildCst_self / b              roi.ts:11–33
ROI broad  (days)         ROI_b     = subtreeBuildCost / b              roi.ts:42–58, report.ts:425

Input payback narrow      IPB_n     = inputBuffer7_self    / b          report.ts:429–432
Input payback broad       IPB_b     = subtreeInputBuffer7  / b          report.ts:429–432
```

All four return `null` when capex is zero or `b ≤ 0`. Narrow asks "how many days for this
stage's building (incl. habitation) to pay for itself"; broad asks the same for the entire
chain's demand-prorated capex. The input paybacks measure how many days of profit it takes to
recoup a 7-day input stockpile — narrow for the top stage, broad for every stage in the tree.
(`computeInputPayback` in `src/core/inputPayback.ts:9–31` is the same formula as `IPB_n`, since
`inputBuffer7 = 7 · (cost + WfCst) · runsPerDay`.)

Opportunity cost appears in the payload as `totalOpportunityCost`, `profit`
(= `finalProfit`), `adjProfitPerOutput` and `profitPerDay` — informational; it does not drive
the ranking.

## 7. How settings change the math

### Exchange (region)

`exchange ∈ {ANT, CIS, ICA, NCC, UNV}` (displayed as ANT/BEN/HRT/MOR/UNV,
`src/lib/exchanges.ts:3–9`). It selects:

* all market prices — `PricesMap[ticker][exchange]` (`price.ts:4–17`);
* the cost columns `WfCst-<EX>`, `Deprec-<EX>`, `AllBuildCst-<EX>` (`getCostColumnNames`,
  `engine.ts:27–38`) — i.e. workforce consumables, depreciation, and construction were
  *pre-priced at that exchange's ask prices* by `calculate-dynamic-costs.ts`;
* the BestMap file `best-recipes-<EX>-bid[.Extraction].json` (`report.ts:90–92`), except UNV,
  which reuses ANT's BestMap.

### Pricing mode (`priceType ∈ {bid, ask, pp7, pp30}`)

* **Sell side:** outputs and byproducts are valued at the selected type (default `bid` —
  conservative: sell into the standing bids).
* **Buy side:** inputs are always bought at **ask** (cross the spread), except on UNV
  (`getInputPriceType`, `engine.ts:19–21`).
* **pp7 / pp30** are 7-/30-day rolling volume-weighted average prices (VWAP) with outlier
  clipping, computed offline (`scripts/calculate-vwap.ts:1–20`).
* **UNV** has no order book, hence no bid/ask: the report refuses bid/ask there
  (`report.ts:260–274`), both sides use the selected pp7/pp30, and the cost columns switch to
  the `-UNV7` / `-UNV30` variants (`engine.ts:29–31`).

### Extraction vs non-extraction mode

`extractionMode=true` (ANT only, `report.ts:117–166`):

1. loads the `-Extraction` BestMap (`report.ts:91–92`), and
2. merges `ANT-expandedrecipes-dynamic.csv` into the recipe map — per-planet extraction recipes
   (COL/RIG/EXT resource extraction, with planet-specific building requirements such as
   MCG/AEF/SEA/… surcharges baked into their cost columns by
   `scripts/calculate-expanded-costs.ts`).

Mathematically nothing changes; the recipe set grows. Raw materials (ores, gases, liquids)
that are otherwise BUY-only leaves acquire MAKE branches, so chains can extend down to planet
extraction. This is also why the scenario caches are cleared per request (`report.ts:39–41`):
extraction mode is not part of the memo key.

### Force/exclude constraints

`forceMake` / `forceBuy` (per ticker) suppress the BUY or MAKE branch respectively
(`engine.ts:1163–1167, 1197`); `forceRecipe` / `excludeRecipe` whitelist/blacklist recipe
variants per ticker (`engine.ts:992–1025`); `forceBidPrice` / `forceAskPrice` override prices
across all exchanges before analysis (`report.ts:171–221`). Constraints are validated for
contradictions first (`report.ts:291–391`).

## 8. Worked example

Round numbers, one two-stage chain. Root ticker **AB**, recipe `AB_1`:

* outputs 2 AB per batch, `runsPerDay = 2` (12 h/run) → capacity 4 AB/day
* `Area = 40 m²`, `WfCst = 60`, `Deprec = 40` per batch, `AllBuildCst = 120 000`
* inputs per batch: 4 × X, 1 × Y;  prices: AB bid 500, Y ask 100, X ask 30

Child option for X (already computed one level down): `COGM_X = 20`,
`baseProfitPerOutput_X = 8` (X sells at bid 28), capacity 40 X/day
(`Output1CNT = 10`, `runsPerDay = 4`), `Area = 20 m²` → `selfAreaPerDay = 20/40 = 0.5`,
`AllBuildCst = 30 000`.

Branch counts: X has BUY + 1 MAKE = 2, Y has BUY only = 1 → `2 × 1 = 2` scenarios.

**Scenario A — `Buy X | Buy Y`:**

```
totalInputCost      = 4·30 + 1·100                = 220
totalProductionCost = 220 + 60 + 40               = 320
totalOutputValue    = 2 · 500                     = 1000
baseProfit          = 1000 − 320                  = 680 /batch
baseProfitPerDay    = 680 · 2                     = 1360
COGM                = 320 / 2                     = 160 /unit
subtreeArea         = 40   (no MAKE children)
PA                  = 1360 / 40                   = 34.0 /m²/day
ROI_n = ROI_b       = 120 000 / 1360              = 88.2 days
inputBuffer7        = 7·(220+60)·2                = 3920 → IPB = 3920/1360 = 2.9 days
```

**Scenario B — `Make X_1 [ … ] | Buy Y`:**

```
totalInputCost      = 4·20 + 100                  = 180
totalProductionCost = 180 + 60 + 40               = 280
baseProfit          = 1000 − 280                  = 720 /batch  → 1440 /day
opportunityCost     = 4 · 8                       = 32 /batch
finalProfit         = 720 − 32                    = 688 /batch
COGM                = 280 / 2                     = 140 /unit
```

Tree aggregation at root capacity (demand 4 AB/day ⇒ `runsRequired = 2 = runsPerDay`):

```
child demand   = 4 X/batch · 2 runs/day           = 8 X/day   (20% of X's 40/day capacity)
child area     = 0.5 · 8                          = 4 m²
children@cap   = (4 / 2) · 2                      = 4 m²
subtreeArea    = 40 + 4                           = 44 m²
PA             = 1440 / 44                        = 32.7 /m²/day

child capex needed = 30 000 · (0.8 / 4)           = 6 000     (X needs 0.8 of its 4 runs/day)
subtreeBuildCost   = 120 000 + 6 000              = 126 000
ROI_n = 120 000/1440 = 83.3 d;  ROI_b = 126 000/1440 = 87.5 d
```

**Verdict:** making X raises daily profit (1440 > 1360) but costs 4 m² of extractor/refinery
area; per square meter, buying wins (34.0 > 32.7), so `Buy X | Buy Y` ranks first. This is the
point of the metric: the report optimizes *profit density over the whole chain's footprint*,
not margin per unit. Meanwhile the positive `finalProfit` gap (688·2 = 1376 < 1360… i.e.
adjusted profit is *also* lower than Scenario A's base) tells you selling X on the market and
buying it back is not worth vertical integration here.

## Appendix: things worth knowing when trusting the numbers

* **Ranking uses base profit, not opportunity-adjusted profit** (`engine.ts:1394–1397`); the
  adjusted figures are displayed but never ranked on.
* **Deep subtrees (depth ≥ 4) follow the offline bid-priced BestMap**, even when you analyze
  with ask/pp pricing (`report.ts:88–92`, `engine.ts:918–963`).
* **`top3DisplayScenarios` guidance is inert in the live report path** — `convertToBestMap`
  strips it (`cachedBestRecipes.ts:86,106`), so depth ≥ 4 always collapses to a single best
  chain there.
* **Buying always pays the ask, selling defaults to the bid** — the spread is a real cost in
  every scenario.
* **Fractional buildings** are assumed everywhere in area/capex proration.
* **Depreciation** is production-building cost / 180 days (`calculate-dynamic-costs.ts:598`);
  habitation is in capex (`AllBuildCst`) but not depreciated.
* **Missing prices** are `null`, not 0 (`maps.ts:35–37`): an unpriced input removes the BUY
  branch; an unpriced main output zeroes profit terms but still yields a valid COGM for
  upstream use.
